Write the non volatile block store for an engine control unit and leave it at /app/nvm_store.py.

The program is started once per scenario as `python3 nvm_store.py`, from an empty working directory holding nothing but a copy of your file, and it talks to the flash part over standard input and output. It is started again, over the same flash image, every time the supply is lost, and the run carries on from where it stopped.

The part is a NOR flash of between 12 and 20 sectors, each of 64 to 128 pages, each page 64, 128 or 256 bytes. A page is programmed as a whole and programming only drives bits from one to zero, so programming a page that has not been erased since its last use leaves the bitwise and of the old contents and the new. Erasing is done on a whole sector and takes the device away for three or four ticks, during which a read or a program is refused. On some parts one or two sectors are worn out: from the second erase of such a sector onwards the device reports the erase as finished while a few of that sector's pages keep whatever they held. The exact geometry, the cost of each operation and the length of the erase window arrive at startup and are not the same on every part.

At startup you get one line `BOOT <json>` carrying sectors, pages_per_sector, page_bytes, t_read_ms, t_program_ms, erase_ticks, tick_ms, tick_budget_ms, mount_budget_ms, read_deadline_ticks, the list blocks of the 24 block lengths in bytes, the current tick and the boot count. A line `MOUNT` follows, and when you have recovered whatever you need from the image, print `MOUNTED`.

After that the run is a loop of ticks of tick_ms, ten milliseconds. A tick opens with `TICK n`. Then come zero or more request lines, either `WRITE rid block hex` asking for that block to hold those bytes from now on, or `READ rid block` asking what it holds, where rid is an integer that identifies the request. The line `GO` closes the tick. Read every line up to and including GO before you print anything at all, because a device operation issued earlier would have its reply tangled up with the rest of the tick.

Between GO and the end of the tick you may issue device operations, one per line, each answered by exactly one reply line before you send the next. `OP READ sector page` is answered `DATA hex` with the whole page, or `BUSY` if an erase is in flight. `OP PROGRAM sector page hex` takes exactly page_bytes of data and is answered `OK` or `BUSY`. `OP ERASE sector` starts an erase and is answered `OK` or `BUSY`. `OP STATUS` is answered `READY`, or `BUSY k` with the ticks left of the erase window. Alongside those you print `ACK rid` once, and only once, for a write whose bytes are now safe on the part, and `VALUE rid x` for every read delivered in this tick, where x is the hex of the value, or NONE if that block has never been written, or BUSY if you cannot answer yet. Close the tick with `DONE`. Every read delivered in a tick has to be answered in that same tick. A read answered BUSY is delivered again on the next tick under the same rid, but one that has not been given a value within eight ticks of its first delivery counts as lost. Nothing other than those lines may go to standard output; standard error is yours.

A write is yours to hold the moment it is acknowledged, and nothing else about it is. Until then it may be dropped by a reset without penalty. A read has to answer with the bytes of the most recent write request that has been delivered for that block, whether or not you have acknowledged it yet, or NONE if no write for that block has ever arrived.

The supply goes away between two and seven times per scenario. The process is killed, so nothing in memory survives. The flash image does: a program interrupted part way leaves a prefix of the page written and the rest as it was, an erase interrupted part way leaves a prefix of the sector erased with the page at the boundary half cleared and the rest untouched, and an erase does not resume after the reset. Some of the resets are aimed at an erase and some at the first programs issued after an erase has finished, and one aimed at an operation that never comes happens anyway, at the latest a few hundred ticks later. Nothing outside the part is meant to carry over: the working directory is thrown away and built again from a fresh copy of your file, the directories that user can write to are emptied, any shared memory it owns is removed, and anything it left running is killed even if that process put itself in a new session. Grading does not rest on that sweep being complete. A value you hand back after a reset has to be present in the flash image itself, byte for byte and in one piece, and so does every value you have acknowledged when the run ends, so a block kept anywhere other than on the part counts as lost however well it survives. Then the program is started again, a fresh BOOT and MOUNT arrive, and every block is read back before the workload continues.

Those read backs are what integrity is measured on. After a reset a block has to come back as the newest value you acknowledged, or as a value from a write that had been delivered but not acknowledged when the supply went. An older value, a value belonging to somewhere else, NONE where something was acknowledged, a read that never gets a value instead of BUSY, or a value that cannot be found in the flash image, each counts as one violation. Five things are measured over the ten graded scenarios together, and all five have to hold. Violations have to be zero. The device time spent between MOUNT and MOUNTED may not exceed 8.0 ms on any boot. The device time spent on reads and programs within one tick may not exceed tick_budget_ms, 2.0 ms, on any tick. Every write has to be acknowledged within 35 ticks of its delivery, with none left unacknowledged when the scenario ends. And the part may not be erased more than 6.0 times per 100 acknowledged writes.

Device time is counted as t_read_ms for a read and t_program_ms for a program, whether it returned data or not. STATUS costs nothing and the erase itself costs nothing against the tick it is issued in, since what it costs is the window in which the device will not answer.

Three development scenarios sit in /app/data/dev. Drive a program around them with `python3 /app/tools/devcheck.py /app/nvm_store.py`, which prints the same measurements the graded run prints. The device model in /app/tools/device.py, the driver in /app/tools/harness.py and the metric code in /app/tools/scoring.py are the same ones grading uses, and /app/tools/skeleton_store.py speaks the protocol and stores nothing, should you want the plumbing rather than writing it again. The graded scenarios are not these: there are ten of them, spread over four parts whose geometry is not the development part's, they run between 520 and 1700 writes, and some of them have worn sectors.

Your program runs as an unprivileged user on two cores under Python 3.11 with numpy available and no network, in a seperate process per scenario with nothing carried between them, and anything it writes to its working directory is discarded. Each scenario has to finish within 90 seconds of wall time, which is far more than this needs; the reference takes about a second.

You have 14400 seconds to complete this task. Do not cheat by using online solutions or hints specific to this task.
